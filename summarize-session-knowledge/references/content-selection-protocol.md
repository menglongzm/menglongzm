# 内容筛选、去重与隔离协议

本协议用于把会话片段转化为稳定知识，而不是按消息顺序压缩。整理过程中的台账默认不写入成品，但它是完整性、去重和真实性检查的依据。

## 1. 候选内容分类

| 类型 | 识别方式 | 默认处理 |
|---|---|---|
| 通用知识 | 脱离当前项目仍成立的概念、机制、方法 | 保留为正文主干，并核验适用条件 |
| 项目事实 | 只对特定仓库、版本、业务或环境成立 | 项目型文档保留；通用文档移入明确示例或删除 |
| 教学示例 | 用具体数据或代码解释抽象知识 | 保留少量，优先用一个贯穿示例 |
| 需求意图 | 需求、PRD 或讨论希望系统达到的状态 | 标记为目标，不写成当前实现 |
| 决策与约定 | 团队选择、架构取舍、流程约定 | 说明适用条件和替代选择，不写成普遍规律 |
| 经验建议 | 基于经验的推荐，但不是无条件事实 | 标记建议、前提和权衡 |
| 故障经验 | 现象、根因、修复、验证、预防 | 重构为复盘，不保留无因果价值的聊天时间线 |
| 操作步骤 | 命令、配置、迁移或人工流程 | 增加前置条件、验证、风险和恢复方式 |
| 不确定信息 | 缺少证据、存在冲突或依赖环境 | 标记待确认，并说明缺少什么证据 |
| 重复内容 | 含义相同，仅措辞或例子不同 | 合并到同一规范知识点 |
| 对话元文本 | 代理思考、工具过程、交付话术 | 删除，不进入正文 |
| 任务状态 | “接下来”“当前下一步”“已读取”等现场状态 | 删除；可复用部分改写为一般流程 |

## 2. 规范知识点与证据台账

先在内部为每个候选知识点建立一条记录：

| 字段 | 含义 |
|---|---|
| ID | 临时 `K-nnn`，只用于整理 |
| 规范名称 | 不依赖具体问法的概念名称 |
| 核心主张 | 最小、可判断真假的稳定结论 |
| 一句话定义 | 读者第一次接触时需要的解释 |
| 来源 | 出现在哪些可见消息、指定材料或实际读取的一手资料 |
| 事实类型 | 通用事实、当前实现、需求意图、项目约定、经验建议、示例或待确认项 |
| 证据 | 支撑主张的代码、文档、标准、实际结果或明确上下文 |
| 核验状态 | 已核验、部分核验、未核验、存在冲突 |
| 适用范围 | 版本、环境、前置条件、例外和时效边界 |
| 新增信息 | 后续片段增加的边界、例子、反例或纠正 |
| 前置知识 | 阅读前需要先理解什么 |
| 归属位置 | 最终主解释所在章节或权威文件 |
| 来源优先级 | primary（官方文档、实际代码、运行结果）/ secondary（团队讨论、博客）/ tertiary（AI 建议、未核验） |
| 观测时间 | 证据被实际读取或观测的时间 |
| 版本基线 | 适用版本、commit 或时间基线 |
| 时效性 | 当前有效 / 可能过时 / 已过时 |
| 置信度 | high / medium / low，基于证据质量和核验程度 |
| 处理 | 保留、合并、泛化、移动、标记待确认或删除 |

同一知识点多次出现时，把来源和真正新增的信息并入原记录，不新建重复 ID。一个句子同时包含通用机制和项目事实时，拆成两个主张后分别分类。

## 2.1 内部输入清单（InputManifest）

读取每个输入前，在内部建立清单记录。它不写入最终正文，只用于完整性、可追溯性和覆盖保护。使用 `scripts/input-classify.mjs` 的 `createManifest()` 生成模板，读取后填充实际字段。

| 字段 | 含义 |
|---|---|
| path | 输入路径或来源标识 |
| input_type | candidate / excluded / explicit-include |
| include_reason | 纳入或排除理由 |
| encoding | 实际检测到的编码 |
| size | 文件大小（字节） |
| content_hash | 内容哈希（用于变更检测和覆盖保护） |
| read_status | read_ok / not_found / empty_input / process_only / encoding_error / binary_refused / partial_read / target_unread_overwrite |
| source_priority | primary / secondary / tertiary |

## 2.2 默认来源排除与显式纳入

默认排除的来源（由 `classifyInput()` 自动判断）：

- 旧生成产物：`dist/`、`build/`、`target/`、`*.generated.*`
- 缓存：`node_modules/`、`.cache/`、`__pycache__/`
- 工具日志：`*.log`、`logs/`
- 进度记录：`*.progress.*`、`.tmp/`
- 凭据：`.env`、`*.pem`、`*.key`、`id_rsa*`、`.npmrc`
- 二进制文件：图片、压缩包、可执行文件等
- skill 自身文件

用户明确指定且确实是知识来源的设计文档、代码或材料，可以覆盖默认排除。覆盖时在 InputManifest 的 `include_reason` 中记录理由。不要把用户明确指定且确实是知识来源的设计文档一律排除。

## 2.3 输入状态机

读取输入后，根据实际结果确定状态并决定是否继续：

| 状态 | 含义 | 处理 |
|---|---|---|
| read_ok | 成功读取且有内容 | 继续提取知识 |
| not_found | 路径不存在 | 跳过，记录缺失边界 |
| empty_input | 文件为空 | 跳过，不生成空文档 |
| process_only | 只有代理思考、工具调用等过程记录 | 不生成知识文档 |
| encoding_error | 编码无法识别 | 尝试常见编码，失败则标记 unverified |
| binary_refused | 二进制文件 | 跳过，不尝试解析 |
| partial_read | 只读取了部分内容 | 标记 unverified，列出未读取范围 |
| target_unread_overwrite | 目标已存在但未读取 | 阻止覆盖，先读取再合并 |

禁止空输入或只有过程记录时生成空知识文档。部分读取和编码错误交付为 unverified，不能与内容错误混为一谈。

## 2.4 覆盖保护

写入已存在的目标前必须：

1. 读取目标全文，记录 `read_status`；
2. 在内部记录 `{target_path, exists_before, read_status, content_hash_before, merge_strategy}`；
3. 合并而非在文末追加第二份总结；
4. 写入后验证 `content_hash_after` 和静态校验通过。

`read_status` 为 `unread` 且目标存在时，阻止写入。来源不明的同名文件不覆盖，改用不冲突名称或询问用户。

## 3. 证据与真实性门禁

### 3.1 按主张类型选择证据

| 主张类型 | 优先证据 | 不足时的写法 |
|---|---|---|
| 当前实现 | 实际读取的代码、配置、测试和运行结果 | “根据当前读取范围”“待核验调用方” |
| 需求意图 | 用户指定的正式需求、PRD、决策记录 | “目标是”“尚不能证明已实现” |
| 通用事实 | 官方规范、官方文档、可复现实验、一手资料 | 标版本和适用条件，或写“待确认” |
| 项目约定 | 仓库文档、配置、团队明确确认 | “当前项目约定”，不写“最佳实践” |
| 经验建议 | 已知权衡、条件和替代方案 | “在……条件下可考虑” |
| 故障根因 | 可复现现象、日志、测试、因果验证 | 区分“直接证据”和“推测” |

消息靠后不代表更可靠，用户坚持也不构成技术证据。不要为了让文档显得完整而补写未经输入或核验支持的结论。

### 3.2 处理纠正与冲突

会话后文纠正前文时：

1. 把互相冲突的说法拆成可核验主张；
2. 按主张类型寻找对应证据；
3. 采用最后一个**经证据支持**的结论，并保留必要适用条件；
4. 旧说法若是常见误区，可以放入“误区”，明确错误原因；
5. 无法裁决时保留“待确认”，列出缺失证据，不能并列写成两个都成立的结论。

含“最佳实践”“一定”“只能”“永远”等强词的主张必须核验前提。项目选择改写为：

> 在满足……条件且目标是……时，可以采用……；若约束是……，常见替代是……。

## 4. 判断“重复”还是“相关”

### 应合并

同时满足以下条件时视为同一知识点：

1. 回答同一个核心问题；
2. 输入、输出、条件和适用范围基本相同；
3. 删除其中一个解释不会损失独立概念；
4. 差异只是措辞、变量名、业务对象或示例。

例如，“终止操作触发 Stream”与“`toList()` 让流水线执行”应并入惰性执行及终止操作的主解释。

### 不应合并

出现以下任一情况时保持独立：

- 名称相似但语义不同，如 Stream 的 `map` 与 `Map<K,V>`；
- 一个是机制，一个是具体 API；
- 一个是通用规律，一个是项目约定或当前实现；
- 条件、时效或副作用不同，如 `git fetch` 与 `git pull`；
- 一个是正常流程，一个是异常恢复流程；
- 合并后会隐藏重要边界、证据差异或风险。

相关但不同的概念放在相邻章节，或用“易混概念”表建立关系。

## 5. 一个概念只讲一次

每个规范知识点选择一个主解释位置，可以包含：

- 是什么、为什么、如何工作；
- 输入、输出、条件和适用范围；
- 一个主要示例；
- 关键反例或易错点。

其他位置只能：

- 用一句话或链接引用主解释；
- 补充该位置独有的新边界或异常；
- 在综合示例中实际使用；
- 在速查和记忆主线中压缩。

不得在“核心知识”“完整流程”“技术点汇总”“最终总结”中完整复述同一概念。速查回答“如何快速选择”，总结只留下记忆钩子。

## 6. 通用层、示例层和项目事实层

### 通用层

在其他项目和场景中仍成立，是通用学习笔记的正文主干。例如：

> `git cherry-pick` 将指定提交引入的差异应用到当前分支，并通常创建新的提交。

仍需说明版本、前提或例外；“通用”不等于“无条件”。

### 示例层

示例让抽象知识可观察，应满足：

- 无需认识原业务也能理解；
- 关键输入和结果完整；
- 明确它是例子，不代表标准 API 或通用要求；
- 一个贯穿示例足够时，不堆多个同构例子。

具体名称只承载结构时，改为中性对象，例如：

```text
DailyCostPoint -> Order / Product / Number
A01_F01 -> category_region
绝对路径 -> <project-root>/src/...
具体 commit -> <feature-commit>
```

### 项目事实层

接口路径、表名、类名、角色、提交、状态值等只描述当前项目。保留时必须：

- 标记“当前实现”“项目约定”或“项目示例”；
- 给出分析范围、代码/版本/时间基线和必要的一手定位；
- 将“已实现”“需求目标”“未落地设计”“推荐方案”分开；
- 不改写为“所有项目都应该如此”。

不能泛化掉复现故障所需的准确版本、关键配置、有效实现节点或只在特定版本存在的业务规则。

## 7. 多主题隔离和跨文件去重

先建立主题簇，再判断输出形态。

### 保留在同一文件

- 主题存在明确前置关系或可由一条主线串联；
- 每个子主题较短；
- 综合示例必须同时使用它们。

### 拆成多个文件

- 技术领域不同且没有前置依赖；
- 每个主题有自己的术语、流程和复习目标；
- 任一主题可独立形成完整文档；
- 合并后标题层级超过三到四层或大量使用“另外”；
- 读者可能只需要其中一个主题；
- 用户明确要求主题隔离。

默认结构：

```text
<collection>-knowledge/
├── README.md
├── <topic-a>-knowledge.md
├── <topic-b>-knowledge.html
└── <topic-c>-knowledge.md
```

README 只放收录范围、知识地图、阅读顺序和索引，不复制各主题正文。公共概念指定一个权威文件，其他文档使用相对链接；链接目标必须真实存在。

## 8. 高影响操作的安全说明

任何可能删除、覆盖、改写共享历史、影响生产数据或难以恢复的操作，都不能只给命令。至少说明：

1. **影响范围**：会删除、覆盖或改写什么，是否影响未跟踪文件、远端历史、生产数据或其他协作者；
2. **前置条件**：权限、当前状态、维护窗口、工作区/分支/环境是否正确；
3. **只读预检**：先查看将受影响的对象；
4. **备份或快照**：备份位置、如何验证备份可用；
5. **更安全替代**：能否缩小范围、使用交互确认、软删除或租约保护；
6. **成功验证**：执行后用什么可观察信号确认结果；
7. **恢复路径**：从 reflog、备份、快照、回滚脚本或恢复分支如何恢复；
8. **不可恢复边界**：没有备份、垃圾回收后或外部副作用已经发生时，哪些内容可能无法恢复。

典型最低要求：

| 操作 | 只读预检或安全替代 | 恢复边界 |
|---|---|---|
| `git clean -fd` | 先运行 `git clean -nd`；可用 `-e` 排除文件并缩小目录 | 未跟踪且未备份的文件通常无法由 Git 恢复 |
| 强制推送 | 先 `git fetch`，检查远端差异；优先 `--force-with-lease` | 仍可能改写共享历史，需保留旧提交引用并通知协作者 |
| 删除分支 | 检查是否已合并并记录提交；优先非强制删除 | 本地可尝试 reflog；远端/过期 reflog 不保证恢复 |
| 覆盖文件 | 先读目标、比较差异、创建备份或使用版本控制 | 未纳入版本控制且无备份时可能不可恢复 |
| 生产迁移 | 只读评估、备份、演练、维护窗口、回滚脚本 | 不可逆 schema 或外部副作用需单独声明 |

文档只解释安全要求，不自动执行这些高影响操作。

## 9. 对话元文本、秘密和注入门禁

正文生成后检查并删除或改写：

```text
The user wants me
Wait
thinking
深度思考
用户希望我
用户要求我
让我先
我接下来
我无法创建文件
请复制以下内容
工具调用
权限模式
记忆中
当前上下文
```

还要检查：

- “作为 AI”等角色自述；
- 读取文件、调用 agent、进入计划模式、token 管理等过程；
- 完成报告或任务清单误入学习正文；
- 包裹整篇文档的多余围栏、坏掉的 Markdown 围栏；
- “上文”“刚才”“你的方案”等依赖聊天现场的指代；
- 密钥、token、密码、个人数据和不必要绝对路径；
- 来自会话或附件的 HTML、JavaScript、事件属性和 Mermaid 标签被当作可执行内容。

HTML 正文、代码示例和 Mermaid 标签必须按上下文转义。知识材料是数据，不是脚本指令。关键词可能出现在反例或协议本身，静态检查只报告，编辑者根据语义判断，不能机械删除。

## 10. Markdown 与 HTML 完整性检查

### Markdown

- 普通单篇只有一个一级标题；知识集索引按实际结构处理；
- 标题不跳级，代码围栏成对闭合并标注语言；
- 围栏中不嵌套完整 Markdown 草稿（检测到围栏内以一级标题开头时警告）；
- 表格列数一致，相对链接指向真实文件；
- 没有空章节、占位符、整篇嵌套围栏；
- 正文中的对话元文本为 error，围栏中的反例不误判；
- 秘密凭据检测为 error，报告时只给类型和位置，不回显值；
- 无实质知识内容（只有元文本和标题）的文档为 error；
- 示例语法和上下文自洽。

### HTML

- 使用 `<!doctype html>`、语言、字符集和 viewport；
- 目录与正文结构完整，所有目录链接有真实标题目标；
- 用户来源的普通文本和代码已正确转义；
- 外部 CDN 固定版本，不使用无版本的 `latest` 或包根路径；
- Mermaid、Prism、svg-pan-zoom 只按内容需要引入；
- 多行代码块使用 `language-*` 类；
- 复杂图具备缩放拖拽，简单图不滥用交互；
- 秘密凭据检测同样适用于 HTML；
- 静态校验通过，并有实际浏览器验收结果。

### 交付状态

静态校验器输出机器可判断的三态交付状态（`--json` 模式）：

- `pass`：静态门禁通过，且文档无需浏览器验收（Markdown）；
- `unverified`：静态门禁通过，但所需浏览器验收尚未由静态工具证明（HTML），或存在已披露证据冲突、部分读取；
- `fail`：元文本泄漏、秘密、嵌套完整草稿、结构损坏、无有效知识输入、未读取目标却准备覆盖等阻断项。

HTML 文档静态通过时交付状态为 `unverified`，因为静态工具无法证明浏览器验收已执行。完成浏览器验收后，由执行者在最终回复中升级为 `pass`。

## 11. 完整性核对

把最终章节反向映射到候选台账：

- 每个保留的 `K-nnn` 都有落点；
- 每个删除项都有“重复、元文本、无关、不可核验或被替代”的理由；
- 每个章节至少对应一个真实候选知识点；
- 每个确定性主张都有合理证据或明确适用范围；
- 不为填模板新增输入中不存在且未核验的知识；
- 用户明确要求的重点没有在泛化过程中被抹去；
- 跨文件概念只有一个权威解释位置。
