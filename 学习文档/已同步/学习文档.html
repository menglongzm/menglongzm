学习文档：Git 工作流与合并冲突复盘

本文汇总一次真实开发会话中的四类知识：按场景分类的 Git 命令速查（含 IDEA 图形化对应）、"远程功能分支 + 本地测试分支"的测试工作流、一次单元测试实践，以及一次合并冲突 → 错误推送 → revert → cherry-pick 挽救的完整复盘。

范围：案例均为项目实况（功能分支 XQ-#16441冻品订单报价审批页新增产品名称筛选-0709-zsl），提交哈希只用于复盘对照；命令本身可迁移到任意 Git 仓库。PowerShell 环境下部分命令需加引号（如 git log "@{u}..HEAD"）。

1. 一句话定位

这份文档回答三个问题：

  1. 怎么查、怎么比、怎么撤销——日常 Git 操作速查（命令 + IDEA 路径双份）；
  2. 测试代码怎么放——业务代码进功能分支、测试代码留本地测试分支的工作流；
  3. 错误合并推上远程后怎么救——一次真实事故的完整处理链：revert 撤销、历史改写检测、cherry-pick 精确重放。

2. Git 命令速查

2.1 查看状态

git status              # 查看当前分支状态
git branch              # 查看本地分支列表
git branch -vv          # 查看分支及对应的远程追踪分支

2.2 比较差异

# 本地已提交但未推送 vs 远程
git log origin/HEAD..HEAD
git log HEAD..origin/HEAD
git diff origin/HEAD..HEAD

# 当前分支 vs 远程对应分支（PowerShell 需加引号）
git log "@{u}..HEAD"
git log "HEAD..@{u}"
git diff "@{u}..HEAD"

# 两个本地分支比较
git diff A..B
git diff --name-only A B          # 只看文件名
git difftool A B                   # 图形化比较

# 当前分支 vs 远程对应分支
git fetch                          # 先更新远程信息
git diff @{upstream}
git diff --name-only @{upstream}
git log @{upstream}..HEAD          # 本地比远程多哪些
git log HEAD..@{upstream}          # 远程比本地多哪些

2.3 分支操作

# 创建新分支
git checkout -b test-branch

# 切换分支
git switch 分支名
git checkout 分支名

# 删除本地分支
git branch -D 分支名

# 移除远程追踪关系
git branch --unset-upstream 分支名

2.4 丢弃修改

git checkout -- .        # 丢弃已修改但未 add 的文件
git restore .              # 同上（新版 Git 推荐）
git clean -fd             # 删除所有未跟踪文件和目录（永久删除，慎用）

2.5 暂存与提交

git stash push -m "描述"   # 暂存当前修改
git stash pop              # 恢复最近一次暂存
git add .                  # 添加到暂存区
git commit -m "描述"       # 提交到本地分支

2.6 远程操作

git fetch                  # 更新远程分支信息（不合并）

3. Git 命令与 IDEA 对应表

IDEA 对 Git 的支持非常完善，几乎所有命令都有对应的图形化操作。

Git 命令IDEA 操作路径

git branch / git branch -vv右下角分支切换器 / Git 工具窗口 → Branches
git logGit 工具窗口 → Log 标签页
git diff A..BGit → Compare with Branch...
git diff --name-only比较时左侧只显示变更文件列表

git checkout -bGit → New Branch...

git commitCommit 按钮（Ctrl + K）

常用场景快速操作：比较两个分支差异用 Compare with Branch...；丢弃所有未提交修改用 Rollback...（或右键项目根目录 → Git → Rollback...）；创建本地测试分支用右下角分支名 → New Branch...；暂存修改用 Stash Changes...。复杂操作（如 git clean）可以在 IDEA 内置 Terminal 中执行。

4. 测试分支工作流

核心思想：业务代码进功能分支（远程同步），测试代码留在本地测试分支（不推远程），功能分支合并 dev 时天然干净。

下图回答：测试代码放在哪里、测试通过后各分支如何处理？

维度方案优势
功能分支只含业务代码，直接合并 dev，无需手动删除测试代码
测试分支本地管理，不推远程，不污染远程仓库，用完即删
测试报告本地生成、本地留存，不占用远程空间，按需查看
代码隔离业务和测试物理隔离，功能分支提交历史清晰

4.1 完整操作步骤

  1. 确认当前在功能分支，业务代码已开发完成（git branch 输出 * XQ-#16441...）。
  2. 从功能分支切出本地测试分支：git checkout -b local-test-#16441，用 git branch -vv 确认没有 origin/ 前缀。
  3. 在测试分支上添加测试代码：后端建 src/test/java/... 目录，前端建 tests/unit/...（jest.config.js、setup.js、*.spec.js 等）。
  4. 运行测试：后端 mvn clean test；前端 npm run test:unit。
  5. 测试通过后生成测试报告（保存在本地，不上传）。
  6. 切回功能分支，合并到 dev：git switch 功能分支 → git status 确认只有业务代码 → git checkout dev → git merge --no-ff 功能分支。
  7. （可选）删除本地测试分支：git branch -D local-test-#16441；后续需要修改测试时可随时重新切出。

4.2 关键注意事项

  • 测试分支不要推送到远程：git push -u origin local-test-#16441 是错误操作，什么都不做即可。
  • 测试报告保存在本地：如《代码检查报告_#16441...md》《单元测试报告_#16441...md》。
  • 业务代码有变更时同步测试分支：切回测试分支后 git merge 功能分支。
  • .gitignore 不需要排除测试代码：因为测试分支本身不推远程。

6. 合并冲突复盘

本次问题主要经历了四个阶段。下图回答：错误合并推上远程后，每一步用什么命令、为什么不能用 merge 直接挽救？

6.1 阶段 1：第一次合并时，冲突处理不完整

最初功能分支中已经实现了产品名称下拉筛选（下拉框、产品列表接口、allProductList、productOptions、productCode 查询参数、初始化加载、名称/编码过滤、查询重置页码）。第一次合并到本地 dev 时 toApproval.vue 发生冲突，解决时混合保留了两边代码：

  • 模板保留了 dev 的产品名称普通输入框；data()、mounted() 也保留了 dev 的版本；
  • methods 却保留了功能分支的产品列表方法。

结果：有 getAllProductList()、有 productProductData()，但页面仍是普通输入框，没有下拉选项状态、没有调用产品列表接口。

教训：Git 只负责判断冲突标记是否被删除，不会判断业务代码是否完整。错误结果仍然可以提交和推送。

6.2 阶段 2：错误合并结果被推送到远程 dev

第一次错误合并产生了 Merge commit 5ac534f87 并被推送到远程 dev。当时 GitLab 同时显示功能提交 0fc15fff5（新增下拉列表筛选商品名称）和合并提交 5ac534f87——这不是重复上传：功能提交在功能分支上，合并提交记录两个分支之间的合并关系。

6.3 阶段 3：使用 Revert 恢复远程 dev

git revert -m 1 5ac534f87 --no-edit
  • 产生反向提交 d615fc2e5；git revert 不删除历史，只创建一个新提交抵消目标提交的代码效果；
  • -m 1 表示以 Merge commit 的第一个父提交（合并前的 dev）作为主线；
  • 推送后远程 dev 成功恢复到合并前的代码效果。验证：git diff 8cccb2c8b HEAD -- src/.../toApproval.vue 无输出。

6.4 阶段 4：后续远程 dev 的历史被改写

git merge-base --is-ancestor c5b290930 origin/dev   # 结果为否

功能提交 c5b290930 不再是当前远程 dev 的祖先提交，说明远程 dev 的历史被重置、改写或换成了另一条提交历史，而不是单纯的"后续提交覆盖了功能代码"。但原功能提交仍安全保存在功能分支中。此时不能直接 merge 整个功能分支（携带大量旧 merge、revert 历史），正确方法是 git cherry-pick c5b290930，只把该提交的代码差异重新应用到最新 dev。

6.5 最终采用的处理方案

  1. 最新远程 dev 作为基线：git fetch origin → git switch dev → git pull --ff-only origin dev（当时最新为 fb3707686）。
  2. Cherry-pick 原功能提交：git cherry-pick c5b290930；因两条历史都修改了 toApproval.vue，发生冲突。
  3. IDEA 可视化解决冲突：Current / Yours / HEAD 为当前最新 dev；Incoming / Theirs 为要引入的代码；Result 为最终结果。逐段保留：从功能提交保留两个子页面标题、产品名称下拉框、产品列表 API、allProductList/productOptions/productCode、getAllProductList()/productProductData()、查询重置页码；从最新 dev 保留"丢单待确认"逻辑：
if (Number(cellValue) === 2 && Number(row.approvalStatus) !== 3) {
  return { text: '丢单待确认', color: '#F56C6C' }
}

Cherry-pick 成功生成新提交 39f3c28a6 完善产品名称下拉筛选。检查结果：只领先远程 dev 一个提交、只修改一个 Vue 文件、没有冲突标记、没有未合并文件、推送是 Fast-forward、ESLint 为 0 errors / 5 warnings（原文件已有格式警告）。

6.6 最终代码实现内容

  1. 两个子页面都有对应标题：searchType === 1 显示"待我审批({{ toDoNum }})"，否则显示"全部"。
  2. 搜索选项保持右对齐：main-title 用 display: flex; align-items: center; justify-content: space-between;，标题在左、搜索项整体在右。
  3. 产品名称下拉筛选：el-select 使用 filterable remote clearable + :remote-method="productProductData" + @change="search"；显示 productName、选中值为 productCode、支持按名称或编码过滤、选择或清空后重新查询。
  4. 搜索重置分页：search() 中 this.page.currentPage = 1 后调 getTableData()，并 $bus.$emit('updateCornerIcon')。
  5. 保留最新业务逻辑：没有用旧版文件整体覆盖最新 dev。

7. 关键 Git 命令详解

7.1 常用检查与切换命令

命令作用本次案例要点
git status查看分支、未提交修改、暂存文件、未跟踪文件，以及是否处于 merge/rebase/cherry-pick 中发现未跟踪项 nul，不要用 git add . 以免夹带无关文件
git fetch origin更新远程跟踪引用，不修改本地文件、不自动合并检查远程是否变化的安全命令
git switch dev切换到本地 dev 分支，不会自动更新远程代码分支名含 # 时建议加引号
git pull --ff-only origin dev仅允许 Fast-forward 更新；本地与远程分叉时直接失败，不自动生成 Merge commit比普通 git pull 更安全
git merge-base --is-ancestor <commit> origin/dev判断某提交是否仍是远程分支的祖先返回失败证明远程 dev 历史被改写
git branch --all --contains <commit>查看哪些分支仍包含该提交确认提交仍可找回
git log --oneline origin/dev..HEAD显示本地领先远程的提交推送前确认只会推送一个提交
git diff --stat origin/dev...HEAD查看相对远程修改了哪些文件及规模防止夹带其他文件（1 file changed, 52 insertions）
git diff origin/dev...HEAD -- <file>查看最终提交的实际代码变化确认产品筛选被恢复、最新逻辑未删除
git diff --check origin/dev...HEAD检查行尾空格等格式问题没有输出表示通过
git grep -n -E "^(<<<<<<<|=======|>>>>>>>)" HEAD -- <file>检查是否残留冲突标记没有输出表示无残留
git merge-base --is-ancestor origin/dev HEAD判断推送是否 Fast-forward是则普通 push 即可，不需要强制推送
git push origin dev推送本地 dev 新增提交绝不用 git push --force：会改写共享分支历史

7.2 Cherry-pick 系列

命令作用
git cherry-pick <commit>只提取指定提交产生的代码差异应用到当前分支，成功后生成新提交哈希；不合并整段历史
git status / git diff --cc冲突时显示 You are currently cherry-picking...；diff --cc 查看冲突双方与合并结果
git add <file>把已处理的目标文件加入暂存区，告诉 Git 该文件冲突已解决（应指定文件，不要 git add .）
git cherry-pick --continue所有冲突解决并暂存后继续，创建最终新提交（IDEA 自动完成则无需执行）
git cherry-pick --abort放弃当前 cherry-pick，恢复到执行前状态（仅在进行中时可用；已完成则不能撤销最终提交）
git cherry-pick --skip放弃正在应用的提交，继续序列中下一个（只挑一个提交时等于放弃功能，不应使用）

7.3 Merge、Revert、Cherry-pick 的区别

命令作用本次案例
git merge <branch>合并一个分支的提交历史，可能带入多个提交、创建 Merge commit不适合：功能分支包含大量旧 merge/revert 历史
git revert <commit>创建反向提交抵消目标提交的代码效果，不删除历史；撤销 Merge commit 需 -m 1 指定主线用于安全撤销已推送的错误合并
git cherry-pick <commit>只选取一个指定提交的差异应用到当前分支，产生新提交用于在历史被改写后精确重放功能提交

7.4 推送后验证

git fetch origin
git status
git rev-parse HEAD
git rev-parse origin/dev
git log -3 --oneline --decorate origin/dev

如果 git rev-parse HEAD 与 git rev-parse origin/dev 输出相同，本地与远程 dev 已完全同步。

8. 记忆要点与自测

记忆要点

  1. 功能分支管业务、测试分支管测试：测试代码不推远程，合并天然干净。
  2. revert 撤销已推送的错误：不删历史、新建反向提交；撤销 merge 要 -m 1。
  3. merge 带历史、cherry-pick 带差异：分支历史脏时用 cherry-pick 精确重放。
  4. merge-base --is-ancestor 判断提交是否还在分支历史中，是检测"历史改写"的关键工具。
  5. push 前先看 log --oneline origin/dev..HEAD 和 diff --stat：确认只推该推的。

自测问题

  1. 为什么错误合并已经 revert 后，功能提交仍可能"消失"？如何检测？
  2. 功能分支历史很脏（大量 merge/revert）时，为什么 merge 不合适、cherry-pick 合适？
  3. git pull --ff-only 与 git pull 的区别是什么？
  4. 测试分支为什么不需要在 .gitignore 中排除测试代码？
  5. git cherry-pick --abort 与 --skip 分别在什么场景使用？
参考答案
  1. revert 只抵消代码效果，不改变提交存在性；若后续远程历史被改写（reset/换历史），原提交不再属于当前 dev 历史。用 git merge-base --is-ancestor <commit> origin/dev 检测，返回失败即不在历史中。
  2. merge 会把功能分支上的全部历史（包括旧 merge/revert）一起带入，产生大量无关提交；cherry-pick 只提取目标提交的差异，生成干净的新提交。
  3. --ff-only 只允许快进，本地与远程分叉时直接失败，不会在不知情时创建合并提交；普通 pull 可能自动 merge。
  4. 因为测试分支本身就不推送到远程，测试代码永远不会进入共享仓库，无需 gitignore。
  5. --abort 放弃整个 cherry-pick 操作恢复到执行前；--skip 放弃当前这一个提交、继续序列中的下一个（单个提交场景下等于放弃功能）。
