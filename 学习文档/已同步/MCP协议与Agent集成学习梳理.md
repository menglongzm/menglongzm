# MCP 协议与 Agent 集成学习梳理

> 本文系统梳理 MCP（Model Context Protocol）的核心概念、通信机制、实现架构，以及 Agent、MCP 客户端、MCP 服务器三方的职责边界。适合第一次接触 MCP、想理解"模型如何通过协议调用外部工具"的读者，不依赖任何具体项目。

## 1. 一句话定位

MCP 是 AI 应用（Agent）与外部工具/数据源之间的**开放通信协议**：它把"模型想要调用工具"的意图，翻译成一种任何兼容客户端和服务器都能理解的固定消息格式，从而让工具"写一次、处处可用"。

## 2. 整体地图

```text
模型(意图) -> Agent框架(MCP客户端) -> [JSON-RPC管道] -> MCP服务器 -> 真实能力(浏览器/索引库/API)
```

三个角色、两条边界：

- **模型 ↔ Agent 框架**：讲"工具调用意图/结果文本"（对话协议，各家格式不同）；
- **Agent 框架（内嵌 MCP 客户端）↔ MCP 服务器**：讲 JSON-RPC 2.0 + 管道（协议统一，与厂商无关）；
- **MCP 服务器 ↔ 真实世界**：讲具体技术（Playwright、数据库索引等）。

模型全程只看到工具名称和最终文本结果，不知道服务器是一个进程。

## 3. 核心知识

### 3.1 MCP 是什么

- **是什么**：Anthropic 于 2024 年 11 月开源的开放标准，为"AI 应用 ↔ 外部工具/数据"提供统一接入层，常被称为"AI 世界的 USB-C 接口"。
- **消息层**：JSON-RPC 2.0，换行分隔；含标准错误码（-32700 解析错误 ~ -32603 内部错误）及应用级错误码（如 -32602 InvalidParams 用于参数校验失败）。
- **传输层**（可替换，协议逻辑与载体解耦）：
  - stdio：子进程 stdin/stdout，生命周期随管道生灭；
  - Streamable HTTP / HTTP+SSE：远程部署；
  - socket：守护进程多路复用（一个实例服务多个客户端）。
- **五类核心原语**：

| 原语 | 方向 | 作用 |
|------|------|------|
| Tools | 模型→服务器 | 可执行操作，带 inputSchema，经 `tools/list` + `tools/call` 使用 |
| Resources | 模型→服务器 | 可读数据（类远程文件系统） |
| Prompts | 模型→服务器 | 可复用提示模板 |
| Sampling | 服务器→模型 | 服务器请求模型生成内容（经客户端，受用户授权） |
| Roots | 服务器→模型 | 服务器向客户端询问工作区根目录 |

- **双工性**：服务器也可以主动发请求（`roots/list`、日志通知），不是单向调用。

### 3.2 生命周期：握手驱动

```
客户端 spawn 进程(或连 socket/HTTP)
  -> initialize（交换协议版本 + capabilities 能力协商）
  -> initialized 通知
  -> 按能力调用：tools/list、tools/call、resources/read...
  -> 管道关闭即结束（stdio 模式下服务器进程随之退出）
```

`capabilities` 协商在握手时确定双方支持的功能子集，连接前就知道对方能做什么。

### 3.3 工具说明文件（schema 的固化形式）

MCP 客户端的工具清单通常以 JSON 描述，分两层：

**服务器元数据**（如 `SERVER_METADATA.json`）：

| 字段 | 作用 |
|------|------|
| `name` | 服务器唯一名称，即路由键（server_name） |
| `source` | 来源/接入方式（如用户手动添加） |
| `toolCount` | 暴露的工具数量，与 tools/ 下文件一一对应 |

**工具定义**（如 `tools/click.json`）：

| 字段 | 作用 |
|------|------|
| `name` | 工具名（tool_name） |
| `description` | 功能描述，决定模型"何时用"；常隐含前置步骤（如"uid 来自页面快照"暗示先调 snapshot） |
| `inputSchema.properties` | 各参数类型与含义 |
| `inputSchema.required` | 必传参数 |
| `inputSchema.type` | 根类型，固定 `object` |

**推断使用方式的套路**：`description` 决定何时用 → `name` 决定用什么 → `properties.description` 决定参数从哪来 → `required/type` 决定怎么传。

### 3.4 注册配置：为什么"填个命令就能用"

```json
{
  "mcpServers": {
    "my-server": {
      "type": "stdio",
      "command": "my-server",
      "args": ["serve", "--mcp"],
      "env": {}
    }
  }
}
```

这份配置是"启动配方"，只回答"进程怎么拉起"：

- `type` 声明传输方式（stdio = 子进程 stdin/stdout 通信）；
- `command`/`args` 是启动命令与参数（安装后命令已在 PATH 中）；
- `env` 是附加环境变量。

能用 = **协议约定（怎么说话）+ 启动配方（怎么拉起）+ 包内实现（会说话）** 三者的组合。工具作者只需把可执行程序指向这个命令，客户端启动时 spawn 它，握手后 `tools/list` 即可自动发现工具——这就是"零适配接入"。

**路由机制（两层）**：

```
模型视角:  server_name + tool_name  -> 知道发给谁
客户端视角: server_name -> 查注册表 -> 找到进程/端点 -> 转发 JSON-RPC
```

模型从不接触地址/端口；连接信息（命令、URL）只存在客户端的注册配置中。

### 3.5 一次完整的工具调用（贯穿示例）

场景：模型想"查看页面快照，然后点击登录按钮"。

**第 1 步——模型输出意图**（对话消息，不是 JSON-RPC）：

```json
{
  "type": "tool_use",
  "id": "toolu_01AbC...",
  "name": "take_snapshot",
  "input": { "verbose": true }
}
```

**第 2 步——客户端组装 JSON-RPC 请求**（注意两个 id 不同：`tool_use.id` 用于框架内配对；JSON-RPC `id` 用于管道请求-响应匹配）：

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": { "name": "take_snapshot", "arguments": { "verbose": true } }
}
```

**第 3 步——服务器返回结果信封**：

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": { "content": [ { "type": "text", "text": "快照内容..." } ] }
}
```

**第 4 步——客户端回译给模型**（用 `toolUseId` 与之前的调用配对）：

```json
{ "type": "tool_result", "toolUseId": "toolu_01AbC...", "content": "快照内容..." }
```

模型在下一轮基于快照内容（如元素 `uid`）继续输出新的工具调用，循环往复。

### 3.6 模型输出为什么是"确定的"：四重保障

模型的 token 输出在概率上并不确定，但落到框架可解析层面，由四层机制兜底：

1. **训练层**：模型在训练阶段学习工具调用格式（function calling 微调），"会说"协议；
2. **提示层**：框架在系统提示里写明精确格式要求（如 Anthropic 块结构：`type: "tool_use"` + `id` + `input`）；
3. **解码层**：推理引擎做**受控解码（constrained/guided decoding）**——采样时把候选 token 裁剪为"只能匹配预定义 JSON Schema 的下一个 token"，模型想输出非法 JSON 都输出不出来；
4. **解析容错层**：框架解析器做修复（提取 JSON、补括号），失败则重试或报错；框架还会强制校验（如 `tool_result` 必须与 `tool_use` 按 id 一一配对，对不上直接抛错）。

结论：不是"模型碰巧输出固定格式"，而是"协议规定格式 + 模型被训练遵循 + 解码器禁止偏离 + 解析器强制修复"。

### 3.7 MCP 客户端：Agent 接入的五个职责

Agent 接入 MCP 不需要实现协议本身（官方 SDK `@modelcontextprotocol/sdk` 免费提供 `Client` 类），但要具备五个环节：

| # | 职责 | 时序 | 说明 |
|---|------|------|------|
| 0 | **工具清单注入**（listTools） | 最先 | `tools/list` → 把 schema 写进模型上下文；没有它模型不知道有哪些工具 |
| 1 | **意图→请求**（callTool） | 模型输出后 | tool_use 块 → 校验 → 组装 JSON-RPC → 写管道 |
| 2 | **响应→结果** | 服务器返回后 | `result.content` → 校验 → 包装成 `tool_result` 注入对话 |
| 3 | **生命周期** | 全程 | initialize 握手、能力协商、超时/重连、管道关闭清理 |
| 4 | **传输与双工** | 全程 | spawn 进程/连 socket、读写管道；处理服务器主动消息 |

实际集成工作量只有约三处几十行的"接线"代码（清单注入、意图转发、结果回注）+ 框架自带的配置管理与权限确认。自己实现完整客户端（不用 SDK）只在特殊需求下才做（如自研守护进程多路复用）。

### 3.8 服务器实现：四层架构

| 层 | 职责 | 示例 |
|----|------|------|
| 传输层 | JSON-RPC 消息收发 | stdio 读写 stdin/stdout、socket、HTTP |
| 协议层 | 处理 initialize / tools/list / tools/call 及能力协商、双工消息 | 官方 SDK 的 `Server` 类；自研协议分发 |
| 工具层 | 声明工具元数据（name/description/inputSchema）并执行真实逻辑 | 浏览器自动化、索引查询 |
| 生命周期 | 随通信管道生灭 | stdin 关闭即 `process.exit`；守护进程模式则保持存活 |

工具层设计要点：错误分类——"可绕过的条件"（如项目未建索引）应返回指导文本而非 `isError`，否则模型会误判工具集损坏而停止调用；"安全拒绝"（如敏感路径）才保留 `isError` 让模型放弃。

### 3.9 MCP 的职责边界

- **MCP 不负责**把模型输出转成固定 JSON——那是 Agent 框架（harness）的职责；
- **MCP 协议里没有"模型"概念**：它只定义客户端↔服务器之间的消息、schema、信封；模型是 OpenAI 风格（`tool_calls`）还是 Anthropic 风格（`tool_use`）由框架适配，MCP 层无感知；
- **模型输出格式统一 ≠ 工具接入统一**：前者解决"意图的通用语法"（模型↔框架），后者解决"接入的通用管道"（框架↔工具）。没有 MCP 时 N 个工具 × M 个框架 = N×M 份适配；有 MCP 后 = N+M。

### 3.10 MCP vs 插件

两个正交维度：

| 维度 | MCP | 插件 |
|------|-----|------|
| 本质 | 通信协议（怎么说话） | 分发机制（怎么打包、安装、托管） |
| 解决 | 接口统一 | 管理统一（manifest、版本、权限、UI 集成） |
| 通信 | JSON-RPC 2.0 | 宿主私有 API |
| 可移植性 | 高（跨产品通用） | 低（换宿主需重写） |

三者可任意组合：纯 MCP 服务器（无插件形态）、插件内含 MCP 服务器、纯插件（不涉 MCP）。一个能力可同时以两种通道暴露。

### 3.11 易混概念

| 概念 A | 概念 B | 核心区别 |
|--------|--------|----------|
| Agent | MCP 客户端 | Agent 是完整系统（模型+推理循环+调度+上下文），客户端只是其中负责与 MCP 通信的组件 |
| MCP 客户端 | MCP 服务器 | 客户端在管道一端（发起调用），服务器在另一端（执行工具）；同一个产品可身兼两职 |
| 工具说明文件 | 服务器实现 | 前者是模型看到的 schema 描述，后者是真实执行代码 |
| `tool_use.id` | JSON-RPC `id` | 前者框架内配对调用与结果，后者管道内匹配请求与响应 |
| 模型输出格式统一 | MCP 统一 | 前者管模型↔框架，后者管框架↔工具，不是一件事 |

## 4. 常见误区

1. **误区**：MCP 的作用是把模型输出转成 JSON。
   **正确**：那是 Agent 框架的职责（受控解码 + 解析 + 适配）；MCP 只管客户端↔服务器之间的消息。
2. **误区**：模型直接和 MCP 服务器交互。
   **正确**：模型只产生意图，客户端代为组装 JSON-RPC、管理进程与管道，再把结果回注对话。
3. **误区**：插件和 MCP 是同一类东西。
   **正确**：插件是分发/集成机制，MCP 是通信协议，正交可组合。
4. **误区**：工具调用格式靠模型自觉。
   **正确**：格式确定性由训练、提示、受控解码、解析校验四层共同保证。
5. **误区**：MCP 服务器配置里写了地址，所以能连上。
   **正确**：配置只是"启动配方"；路由靠 name 键 + 客户端注册表分发，连接信息（命令/URL）在客户端侧维护。

## 5. 速查

| 想完成的目标 | 使用的概念或操作 | 关键条件 |
|---|---|---|
| 接入一个现成 MCP 服务器 | 注册配置（type/command/args/env） | 命令已装、支持 stdio 或给出端点 |
| 让模型知道有哪些工具 | 客户端 `tools/list` → 注入上下文 | 完成 initialize 握手 |
| 模型要调用工具 | 客户端组装 `tools/call`（JSON-RPC） | 参数符合 inputSchema，required 必填 |
| 处理服务器结果 | 校验 `result.content` → 回注 `tool_result` | 与 `tool_use` 按 id 配对 |
| 写一个 MCP 服务器 | 官方 SDK：Server + StdioServerTransport + ListTools/CallTool handler | 声明 capabilities.tools |
| 判断工具何时可用 | 看 `description` | 常隐含前置步骤（先快照再点击等） |

## 6. 最终记忆主线

```text
三方角色(模型/客户端/服务器)
  -> 两段通信(对话协议 / JSON-RPC管道)
  -> 一个协议(JSON-RPC 2.0 + 五原语 + 能力协商)
  -> 两层实现(客户端五职责 / 服务器四层)
  -> 一个关键认知(MCP 不管模型输出格式)
```

### 必记要点

1. MCP = JSON-RPC 2.0 + 可换传输 + 五原语（Tools/Resources/Prompts/Sampling/Roots）+ 握手能力协商；
2. 通信是三方间接的：模型 ↔ 客户端（意图/结果）↔ 服务器（JSON-RPC/管道）；
3. 模型输出格式由"训练+提示+受控解码+解析校验"四重保障趋于确定；
4. 服务器实现四层：传输、协议、工具、生命周期；
5. 客户端五职责：清单注入、意图→请求、响应→结果、生命周期、传输双工；
6. MCP 与插件正交：一个管接口，一个管分发；
7. 注册配置 = 启动配方；路由靠 name + 客户端注册表。

## 8. 附录：本机环境实况（项目事实，非通用规律）

> 以下为 2026-08 在本机（ZCode 环境）核实到的事实，仅用于对照概念，不作为普遍规律。

- **浏览器自动化服务器**：以"插件 + MCP 服务器"双形态存在——插件清单（plugin.json）描述其为技能包；同时暴露 MCP 工具（快照/点击等）。插件实现位于用户插件缓存目录，由宿主进程以插件宿主模式托管运行。
- **代码索引服务器**：npm 全局包，通过 `serve --mcp` 命令以 stdio 方式注册；进程树显示它由客户端会话进程 spawn 的 `cmd` 包装拉起，8 月 3 日 15:11 的实例与当时新建的会话时间吻合，印证"会话初始化时拉起"。
- **另外两个服务器**（genui、schedule）：无独立进程、无注册表条目，实现在宿主主程序打包文件内，进程内托管。
- **生命周期证据**：多个服务器实例的创建时间分布在 7 月 2 日、7 月 30 日、7 月 31 日、8 月 3 日，同一日多次——符合"客户端启动即拉 + 会话打开补拉，客户端退出即终止"。
- **会话记录位置**：会话输入/输出、agent 配置（含 systemPrompt 字段、工具列表、token 用量统计）保存在 `.zcode/cli/agents/sess_*/agent_*/` 目录；但完整 system prompt（运行时拼装）默认不可见，需开调试日志或代理抓包查看。
