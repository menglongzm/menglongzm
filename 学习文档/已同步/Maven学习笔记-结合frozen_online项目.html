Maven 学习梳理（结合 frozen_online 项目）

本文把 Maven 拆成三个问题来讲：项目需要什么、源码怎样变成产物、多个模块怎样协作。适合已会写 Java 单模块程序、第一次系统接触 Maven 的读者。

范围：内容依据《Maven学习笔记-结合frozen_online项目.md》（更新日期 2026-07-28）。项目示例为 muyuan-slaughter-opms-frozen-cost-accounting，同构工程 muyuan-slaughter-mdm-opms；前端由 Node/Yarn 管理，不在本文范围。文中所有涉及该项目的描述均属"项目示例"，不是 Maven 的通用要求。

1. 一句话定位

Maven 是 Java 项目的依赖管理器、构建工具和项目组织工具。可以把两者对照记忆：

pom.xml = 项目说明书（声明模块、依赖和规则）
Maven   = 按说明书工作的自动化流水线

在本项目中，它负责：组织多模块 → 解析和下载依赖 → 统一依赖版本 → 编译代码与处理资源 → 运行测试 → 打包普通 Jar / 可执行 Fat Jar → 安装到本地仓库或发布到公司 Nexus →（可选）构建并推送 Docker 镜像。

2. 整体地图

下图回答：Maven 的三大能力各包含什么，它们之间如何分工？Maven 的一切功能都可以归入这三大类。

三者对应三个问题：依赖管理回答"项目需要什么"，构建管理回答"源码怎样变成产物"，项目结构管理回答"多个模块怎样协作"。后文第 3 节按这三大能力组织。

3. 核心知识

3.1 依赖管理：管理程序需要的库

依赖管理不只是"下载 Jar"，还包括传递依赖、版本选择、作用域、排除依赖和模块间引用。

3.1.1 依赖坐标：GAV

每个依赖由 GAV 唯一定位：

<dependency>
    <groupId>com.alibaba</groupId>
    <artifactId>easyexcel</artifactId>
    <version>3.3.3</version>
</dependency>
字段含义类比
groupId组织或产品组厂商
artifactId构件名称商品名
version构件版本商品型号

完整坐标写作 com.alibaba:easyexcel:3.3.3。

3.1.2 第三方 Jar 的下载链路

下图回答：声明一个依赖后，Maven 按什么顺序把它放进 classpath？

三个角色的分工：dependency = 下载什么；repositories = 去哪里下载；本地 ~/.m2 = 下载后的本地缓存与本机构件仓库。

3.1.3 传递依赖

如果 A 依赖 B、B 又依赖 C，A 通常间接获得 C。项目示例：job → service → dal，job 直接依赖 service，若 service 依赖 dal，则 dal 通常成为 job 的传递依赖。这减少了重复声明，但也可能带来版本冲突。

3.1.4 版本冲突如何产生

同一坐标出现多个版本时（例如 easyexcel → poi 4.1.2，另一个库 → poi 3.17），运行时通常只能保留一个，否则可能出现 NoSuchMethodError、ClassNotFoundException、NoClassDefFoundError。项目示例：父 POM 用 dependencyManagement 统一锁定 POI 版本：

<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.apache.poi</groupId>
            <artifactId>poi</artifactId>
            <version>4.1.2</version>
        </dependency>
    </dependencies>
</dependencyManagement>

3.1.5 版本冲突调解规则

下图回答：没有强制管理时，多个版本中哪个胜出？

无论哪个版本胜出，运行时通常只保留一个，否则可能出现 NoSuchMethodError 等错误。更可靠的做法：不要依赖"碰巧胜出"，应在 dependencyManagement 中明确统一版本。

3.1.6 排除传递依赖

某库传递引入旧版 POI 时，可用 exclusions 精确排除，然后在当前项目显式声明统一版本：

<dependency>
    <groupId>com.example</groupId>
    <artifactId>report-client</artifactId>
    <version>1.0.0</version>
    <exclusions>
        <exclusion>
            <groupId>org.apache.poi</groupId>
            <artifactId>poi</artifactId>
        </exclusion>
    </exclusions>
</dependency>

exclusions 是处理冲突的精确工具，不能因为"依赖多"就随意排除；排除后应运行测试，确认运行期仍有完整类库。

3.1.7 scope：依赖在什么时候有效

scope编译测试运行/打包典型用途
compile是是是默认依赖
provided是是通常不带入运行包编译期工具，如 Lombok
runtime否是是运行期驱动等
test否是否JUnit、Mockito
import不适用BOM，仅在 dependencyManagement 中使用

provided 的含义：编译时需要，但预期运行环境提供，或它只是编译辅助工具。

3.1.8 模块间互相引用

本项目自己的模块也通过 GAV 引用（项目示例，service 引用 dal）：

<dependency>
    <groupId>org.muyuan</groupId>
    <artifactId>muyuan-slaughter-opms-frozen-cost-accounting-dal</artifactId>
    <version>${muyuan.slaughter.opms.frozen.cost.accounting.version}</version>
</dependency>

在同一次根工程构建中，Maven Reactor 直接使用本次构建产生的 dal 模块，不一定要求它预先存在于远程仓库。若另一个独立工程要引用该模块，通常需要先 install 到本机，或 deploy 到公司 Nexus。

3.2 构建管理：把源码变成可交付产物

Maven 构建不是单独动作，而是一条由生命周期阶段组成的流水线。

3.2.1 三套生命周期

生命周期作用
clean删除上一次构建产物
default编译、测试、打包、安装、发布
site生成项目站点和报告

最常使用的是 clean 和 default。

3.2.2 default 生命周期的关键阶段

下图回答：default 生命周期各阶段按什么顺序执行，执行后阶段是否包含前阶段？

阶段作用
validate检查项目是否可构建
compile编译主代码
test编译并运行单元测试
package打成 Jar/War
verify执行额外验证或集成测试检查
install安装到本机 ~/.m2
deploy发布到远程 Maven 仓库

执行后面的阶段会自动执行前面的阶段：mvn package = validate + compile + test + package；mvn install 再多加 verify + install；mvn deploy 再加 deploy。

3.2.3 编译配置

项目示例：父 POM 统一配置 Java 8、UTF-8 编码，并通过 -parameters 保留方法参数名（便于 Spring 参数绑定和反射）：

<properties>
    <java.version>1.8</java.version>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
</properties>

<plugin>
    <artifactId>maven-compiler-plugin</artifactId>
    <version>3.8.1</version>
    <configuration>
        <source>${java.version}</source>
        <target>${java.version}</target>
        <encoding>UTF-8</encoding>
        <compilerArgs>
            <arg>-parameters</arg>
        </compilerArgs>
    </configuration>
</plugin>

含义：允许使用 Java 8 语法，生成面向 Java 8 的 class，源码按 UTF-8 读取。

3.2.4 运行测试与跳过测试

项目示例：service 声明 JUnit 与 Mockito，scope 均为 test，只用于测试、不进入生产运行包：

<dependency>
    <groupId>junit</groupId>
    <artifactId>junit</artifactId>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.mockito</groupId>
    <artifactId>mockito-core</artifactId>
    <scope>test</scope>
</dependency>
mvn package                       # 默认运行测试
mvn package -DskipTests           # 编译测试代码，但跳过测试执行
mvn package -Dmaven.test.skip=true  # 通常连测试编译也跳过

发布前不应习惯性跳过测试；跳过测试只适合临时定位构建问题，不能替代验证。

3.2.5 打包：普通 Jar、Fat Jar 与 War

  • 普通 Jar：库模块（api、dal、service 等）的产物，主要包含本模块的 class 和资源，不塞入依赖 Jar。
  • Fat Jar：启动模块使用 Spring Boot 插件的 repackage，把应用类、依赖和启动结构重新包装为可执行 Jar，可 java -jar 直接运行。
  • War：用于部署到外部 Servlet 容器；当前项目子模块配置 packaging 为 jar，主要走可执行 Jar。

3.2.6 资源复制与资源过滤

两者不是一回事：

资源复制 = 原样放入 target/classes（默认 src/main/resources/** → target/classes/**）
资源过滤 = 复制时替换 ${变量}

过滤示例（启用 <filtering>true</filtering> 后）：

app.name=${project.artifactId}
app.version=${project.version}

项目现状：当前根 POM 配置了资源目录，但未在这些 resource 中明确启用 filtering=true。因此只能确认"资源复制 + 额外收集 Java 目录 XML"，不能确认本项目已启用资源过滤。配置文件中的密码、Token 等敏感值不应通过普通 POM 属性硬编码。

3.2.7 为什么额外打包 src/main/java 下的 XML

Maven 默认不会把 src/main/java 下的 XML 当资源复制。项目示例：MyBatis Mapper XML 放在 Java 目录中（如 ...-dal/src/main/java/.../mapper/DemoMapper.xml），因此父 POM 额外配置：

<resource>
    <directory>src/main/java</directory>
    <includes>
        <include>**/*.xml</include>
    </includes>
</resource>

打包后应同时存在 DemoMapper.class 与 DemoMapper.xml。如果漏掉 XML，编译可能成功，但运行时 MyBatis 可能报 Invalid bound statement (not found)。

3.2.8 插件与生命周期绑定

生命周期只定义阶段，插件负责执行具体工作：compile 阶段由 maven-compiler-plugin 编译，package 阶段由 jar 插件打包，repackage 由 spring-boot-maven-plugin 重包装。项目示例还配置了 maven-antrun-plugin（package 阶段复制 Jar 到根 target）和 docker-maven-plugin（构建、标记、推送镜像）。因此：Maven 是"生命周期调度器"，插件才是具体工人。

3.3 项目结构管理：组织多模块工程

3.3.1 聚合与继承不是一回事

这是多模块项目中最容易混淆的一对概念：

概念配置位置解决什么问题
聚合根 POM 的 <modules>一次构建哪些模块
继承子 POM 的 <parent>子模块复用哪些配置
  • 聚合但不继承：模块 A 被根工程聚合，但它的 parent 是另一个公司父 POM。
  • 继承但不聚合：模块 B 继承某父 POM，但父 POM 没把 B 写进 modules，B 不会随父工程一次性构建。

项目示例：根 POM 同时承担两种角色——通过 modules 组织一次构建（聚合 POM），通过 parent 给子模块继承配置（父 POM）。

3.3.2 Reactor：同一次构建中的模块协调器

下图回答：从根目录执行一次构建时，模块按什么顺序被构建？

Reactor 负责：收集所有 modules → 读取模块依赖关系 → 计算构建顺序 → 在同一次构建中传递模块产物 → 汇总成功、失败和跳过状态。如果基础模块失败，依赖它的后续模块通常会跳过。

3.3.3 继承与统一配置管理

项目示例：父 POM 统一了 Java 版本与编码、平台/业务版本属性、公共依赖、依赖版本表、编译插件、资源目录、下载仓库、发布仓库和 Docker 插件配置。好处是"改一次父 POM → 多个子模块统一生效"；例如调整 java.version 时原则上无需逐个修改子 POM，但实际升级仍需验证源码、插件、依赖和运行环境兼容性。

3.3.4 模块职责与依赖边界

Maven 能声明模块依赖，但不会自动保证架构合理。推荐依赖方向（项目示例）：

api / common
  ↑
dal / external boundary
  ↑
service / job
  ↑
start（最终装配）

应避免底层模块反向依赖启动模块，也应避免模块间循环依赖——Maven 遇到循环模块依赖时无法建立正常构建顺序。

3.4 版本管理：BOM、dependencyManagement 与 dependencies

3.4.1 BOM 是版本目录 POM

BOM 不作为业务 Jar 进入 classpath，它把自身的 dependencyManagement 版本表导入当前项目（项目示例）：

<dependency>
    <groupId>org.muyuan.platform</groupId>
    <artifactId>muyuan-bom</artifactId>
    <version>${muyuan.tool.version}</version>
    <type>pom</type>
    <scope>import</scope>
</dependency>

记忆：BOM = 公司统一版本目录；不是 = 一次性引入所有公司 Jar。

3.4.2 不写 version 时版本从哪里来

子模块写依赖可以省略 version，由父 POM 的 dependencyManagement 或 BOM 提供（项目示例）：

<!-- dal 中声明，无 version -->
<dependency>
    <groupId>org.muyuan</groupId>
    <artifactId>muyuan-core-tool</artifactId>
</dependency>

<!-- 父 POM 的 dependencyManagement 提供版本 -->
<dependencyManagement>
    <dependency>
        <groupId>org.muyuan</groupId>
        <artifactId>muyuan-core-tool</artifactId>
        <version>${muyuan.tool.version}</version>
    </dependency>
</dependencyManagement>

<!-- 属性最终展开为 -->
<!-- org.muyuan:muyuan-core-tool:3.0.1.MY.RELEASE -->

若子模块、父 dependencyManagement、BOM 都没有提供版本，Maven 会报缺少 version。

3.4.3 三者区别

配置是否引入 Jar主要作用
BOM import否批量导入版本目录
dependencyManagement否管理版本、scope、排除等默认规则
dependencies是真正引入依赖

商店类比：BOM / dependencyManagement = 商品目录；dependencies = 实际下单；repositories = 商店地址。

3.4.4 根 dependencies 对子模块的影响

父 POM 的 dependencies 会被子模块继承。项目示例：job 只声明 service，但仍获得父级公共依赖（如 Web、XXL-Job、Lombok 等），还可能获得 service 的传递依赖 dal。最终依赖约等于：

父级公共依赖
+ 子模块直接依赖
+ 直接依赖带来的传递依赖
- exclusions 排除的依赖
→ 再经过版本冲突调解

3.5 仓库与 package、install、deploy

3.5.1 下载仓库

项目示例：根 POM 配置阿里云公共仓（第三方公开构件）与公司 Nexus（内部构件）。Maven 通常先查本地 ~/.m2，没有才访问远程仓库。实际企业环境还可能通过用户 settings.xml 配置镜像、账号和 server——POM 中的仓库不是 Maven 唯一可能使用的下载来源。

3.5.2 三个阶段命令的区别

命令结果位置用途
mvn package当前模块 target得到本次构建产物
mvn install再放入本机 ~/.m2给本机其他独立工程引用
mvn deploy再上传远程 Nexus给同事、服务和 CI 引用

3.5.3 Maven deploy 不是业务上线

Maven 的 deploy 是"发布 Maven 构件"，不是把业务服务部署到生产服务器。两条链路不同（项目示例）：

业务上线链路：Maven package → start Fat Jar → Docker 镜像 → 推 Harbor → 部署到 K8s/服务器
Maven deploy 链路：普通 Jar + POM → Nexus → 被其他 Maven 项目当依赖下载

4. 贯穿示例：一次完整构建

项目示例：在根目录执行 mvn clean package 的典型过程，把前文概念串成一条链路：

  1. clean 删除各模块 target
  2. 读取根 POM 和 modules（聚合）
  3. Reactor 计算模块构建顺序（3.3.2 的依赖图）
  4. 解析父 POM、BOM、dependencyManagement（版本来源）
  5. 从本地 ~/.m2 / 远程仓库解析依赖（下载链路）
  6. 复制和处理资源（资源复制规则，含 Java 目录 XML）
  7. 按 Java 8 编译主代码（编译插件配置）
  8. 编译并运行测试（test scope 依赖生效）
  9. 为各模块打普通 Jar
  10. start 通过 repackage 生成可执行 Fat Jar
  11. 配置的额外插件处理复制或镜像任务

若执行 install，再把各模块构件放入本机 ~/.m2；若执行 deploy，再上传到 distributionManagement 指定的公司 Nexus。

概念 A概念 B核心区别

6. 常见误区与边界

  1. 误区：Maven 只是下载 Jar 的工具。正确理解：它同时是依赖管理器、构建工具和项目组织工具，三大能力见第 2 节地图。
  2. 误区：在 dependencyManagement 中声明了依赖，子模块就不用再声明。正确理解：management 只提供版本规则，不引入 Jar；子模块仍要在 dependencies 中声明才会真正引入。
  3. 误区：版本调解"碰巧胜出"的方案可靠。正确理解：近者优先、先声明优先只是默认规则，应通过 dependencyManagement 明确统一版本。
  4. 误区：发布前跳过测试无所谓。正确理解：跳过测试只适合临时定位构建问题，不能替代验证。
  5. 误区：配置了 resource 目录就是资源过滤。正确理解：复制是原样放入，过滤才替换 ${...} 变量；项目示例当前未启用 filtering=true。
  6. 误区：Maven deploy 就是上线部署。正确理解：deploy 发布构件供其他 Maven 工程使用；业务上线是把应用或镜像运行在目标环境。

其他边界：exclusions 是精确工具，不能随意排除；升级 Java 版本等父 POM 改动仍需验证兼容性；POM 中的仓库不是唯一下载来源（settings.xml 镜像也可能生效）。

7. 速查

目标命令或概念关键条件
清理构建产物mvn clean删除各模块 target
编译主代码mvn compile—
运行单元测试mvn test—
打包mvn clean package默认会经过测试

构建某模块及其所依赖模块mvn package -pl <module> -am-am 同时构建依赖的 Reactor 模块

8. 记忆主线

  • 一句话主线：POM 声明模块、依赖和规则 → Maven Reactor 按依赖顺序构建 → 插件完成资源、编译、测试和打包 → 构件可留在 target、安装到 ~/.m2 或发布到 Nexus。
  • pom.xml = 项目说明书；Maven = 按说明书工作的自动化流水线。
  • dependency = 下载什么；repositories = 去哪里下载；~/.m2 = 本地缓存。
  • BOM / dependencyManagement = 商品目录（只管理版本）；dependencies = 实际下单（真正引入）。
  • 聚合用 modules（一起构建）；继承用 parent（复用配置）。
  • 生命周期：执行后面的阶段自动包含前面的阶段。
  • 资源复制原样搬，资源过滤替换 ${...}。
  • package → target；install → ~/.m2；deploy → Nexus；Maven deploy ≠ 业务上线。

9. 自测问题

  1. dependency 和 repositories 分别决定什么？
  2. dependencyManagement 中声明 EasyExcel 后，为什么子模块还要再声明依赖？
  3. muyuan-bom 为什么写 type=pom 和 scope=import？
  4. Maven 遇到同一依赖多个版本时如何调解？本项目 POI 如何统一？
  5. job → service → dal 中，dal 为什么可能成为 job 的传递依赖？
  6. 聚合和继承分别通过哪个 XML 节点实现？
  7. 为什么根目录一次构建能按 api、dal、service、start 的关系排序？
  8. 资源复制和资源过滤有什么区别？本项目是否明确启用了过滤？
  9. 为什么 Java 目录中的 Mapper XML 需要额外配置？
  10. package、install、deploy 的产物最终分别放在哪里？
  11. 为什么 service 通常跳过 Spring Boot repackage，而 start 执行 repackage？
  12. Maven deploy 为什么不是业务上线部署？
参考答案
  1. dependency 决定下载什么；repositories 决定去哪里找。
  2. management 只提供版本规则，不真正引入 Jar。
  3. 因为它导入的是版本目录 POM，不是业务 Jar。
  4. 默认近者优先、同深度先声明优先；本项目用 dependencyManagement 锁定 POI 4.1.2。
  5. Maven 默认解析直接依赖的传递依赖，除非 scope 或 exclusions 阻止。
  6. 聚合用 <modules>；继承用子 POM 的 <parent>。
  7. Reactor 收集模块并根据依赖图计算顺序。
  8. 复制是原样复制，过滤会替换 ${...}；当前 POM 未明确设置 filtering=true。
  9. Maven 默认不把 src/main/java/**/*.xml 当资源，漏包会导致 MyBatis 运行期找不到语句。
  10. target、本机 ~/.m2、远程 Nexus。
  11. service 是库 Jar；start 是最终可执行应用。
  12. deploy 发布构件给其他 Maven 工程使用；业务上线是把应用或镜像运行在目标环境。
