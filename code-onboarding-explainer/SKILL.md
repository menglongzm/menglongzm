# Code Onboarding Explainer

把陌生代码讲成一张可导航的地图，而不是逐行翻译。目标是让读者先明白代码解决什么问题，再理解当前代码如何执行，最后知道应该去哪里继续阅读或修改。

## 核心原则

1. **先判断范围，再选择结构**：局部表达式、回调、小函数、模块和完整项目使用不同的输出深度；输出结构不是必填清单。
2. **解释主线，不堆背景**：优先说明控制流、数据流、状态变化、调用关系和重要分支。
3. **详细不等于全面**：用户说“详细解释某个函数”时，完整解释这个函数的执行逻辑和直接依赖即可，不自动扩展成语言、协议或框架教程。
4. **概念解释到够用为止**：只解释会影响当前代码理解的语法或框架概念；一个概念只在首次出现时解释一次。
5. **事实与推测分开**：能从代码确认的内容直接说明；无法确认的内容标记为“推测”或“待确认”。
6. **为行动服务**：用户问局部代码时，聚焦当前问题；只有模块或项目范围的请求才提供完整阅读和修改地图。

## 第一步：按范围分流

先判断用户提供的代码范围和问题范围：

- **局部表达式、回调或不超过约 20 行的片段**：使用“局部代码模式”。
- **单个函数或约 20～100 行的小模块**：使用“函数模式”，补充必要的上下文和一个边界情况。
- **完整模块、跨文件调用链或项目**：使用“模块/项目模式”，再使用代码地图、主流程和阅读指南。

代码越小，输出越短。用户要求“详细”只提高关键逻辑的完整度，不改变范围分流结果。

## 开始前的最短调查

只读取理解当前问题所必需的代码及其直接依赖。优先确认：

- 当前代码由谁调用或触发；
- 输入是什么，经过哪些转换；
- 哪些状态被读取或修改；
- 输出如何交给后续代码；
- 哪些条件会改变执行路径。

如果上下文不足，先说明已知范围和缺失信息。只有缺失信息会实质改变结论时才询问用户。不要为了完整而扩展到无关文件、历史背景或框架百科。

## 局部代码模式

局部代码默认使用以下结构，通常控制在 500～900 个中文字符、最多 5 个小标题：

### 作用

用 1～2 句话说明这段代码在整体流程中的职责。

### 直接依赖

只解释理解它必需的外部对象，以及它们如何协作。例如说明 `rl` 从哪里接收输入、`pending` 保存什么，不要展开无关实现。

### 执行逻辑

按真实执行顺序写 3～5 步，说明：谁触发、收到什么、如何转换、如何判断、如何产生后续效果。

### 关键语句

只解释最容易误解的一处或两处代码。例如：

- `pending.get(id)` 取出的值是什么；
- 为什么取出的值可以像函数一样调用；
- 这一调用如何让其他地方的 `await` 继续执行。

### 一个例子与注意事项

用一个具体输入串起数据变化。最多补充 1～2 个会影响理解的边界问题，不主动展开重构建议、性能分析或完整最佳实践。

局部代码默认不输出以下内容，除非用户明确要求：代码地图、完整阅读指南、自检题、长篇语法教程、协议历史和扩展方案。

## 异步与回调代码的必讲闭环

遇到事件监听器、回调、Promise、`Map` 或请求响应匹配时，必须解释下面这个最短闭环：

1. **谁触发当前函数**：例如 `rl` 读取到一行后触发 `line` 回调。
2. **输入是什么**：例如 `line` 是服务器输出的 JSON 字符串。
3. **状态在哪里**：例如 `pending` 保存“请求 ID → Promise 的 `resolve` 函数”。
4. **关键调用做什么**：例如 `pending.get(msg.id)(msg)` 实际调用之前保存的 `resolve(msg)`。
5. **后续如何继续**：说明哪个 `await` 因此拿到结果并继续执行。
6. **何时清理状态**：说明 `delete`、移除监听器或其他清理动作的作用。

只补充形成这个闭环所需的最短上下文，不解释相关函数的全部实现。

## 函数模式

单个函数或小模块可以使用以下结构：

1. 一句话定位；
2. 输入、输出和直接依赖；
3. 3～8 步主流程；
4. 关键分支或关键语句；
5. 一个成功或失败例子；
6. 必要的边界问题。

默认不超过 1,500～2,500 个中文字符。只有用户明确要求系统学习或深入原理时，才补充更完整的语言、框架或协议背景。

## 模块/项目模式

只有在范围较大时才使用完整结构：

### 一句话定位

说明这部分代码解决什么问题，以及它在系统中的位置。

### 代码地图

列出不超过 8 个关键对象及其职责；必要时给出简短调用图。

### 主流程

用 4～8 个有因果关系的步骤说明一次典型执行，并集中列出重要分支。

### 关键实现

选择 2～5 个真正决定行为的代码位置，说明输入、输出、状态变化和隐藏约束。

### 例子、概念与阅读指南

提供一个贯穿例子；只解释最多 3 个必要概念；最后列出 2～5 个高价值的继续阅读或修改位置。

不为了凑结构添加空泛的“优点”“最佳实践”或重复总结。

## 内容取舍

### 应重点解释

- 入口和调用关系；
- 输入如何转换为输出；
- 数据结构和关键字段的变化；
- 会改变路径的条件、异常和状态；
- 模块之间的职责边界；
- 命名无法直接表达的隐含约束。

### 默认省略

- 逐词或逐行翻译；
- 显然的赋值、取值、返回和样板语法；
- 不影响当前逻辑的底层原理；
- 同一概念、流程或结论的重复解释；
- 未经代码支持的设计动机；
- 用户没有询问的重构、性能和生产化建议。

### 删除判断

每段内容加入前先判断：

> 删除这段后，读者还能否理解当前代码如何执行？

如果仍然可以，就删除这段内容。

## 语言与格式

- 使用与用户一致的语言。
- 代码引用使用 Markdown 代码格式；有可靠路径和行号时引用 `路径:行号`。
- 代码片段只保留解释当前职责所需的部分。
- 使用短段落和扁平列表，避免多层嵌套。
- 示例最多 1 个完整主例；只有确实影响理解时才补 1 个边界例。
- 局部代码最多解释 3 个语言或框架概念。
- 不把同一事实分别放在“流程”“概念”和“总结”中重复表达。

## 局部代码示例

对于：

```js
const pending = new Map();

rl.on("line", (line) => {
  const msg = JSON.parse(line);
  if (msg.id !== undefined && pending.has(msg.id)) {
    pending.get(msg.id)(msg);
    pending.delete(msg.id);
  }
});
```

应重点说明：

- `rl.on("line", ...)`：服务器 stdout 每收到一行时触发回调；
- `line`：收到的 JSON 字符串，`JSON.parse` 将其转成消息对象；
- `pending`：保存“请求 ID → Promise 的 `resolve` 函数”；
- `pending.get(msg.id)(msg)`：调用对应的 `resolve(msg)`，让等待中的 `await send(...)` 得到响应；
- `pending.delete`：删除已经完成的请求。

不要在这个局部问题中展开完整的 Node.js 进程通信、MCP 协议历史或所有 JavaScript 基础语法。

## 输出前检查

1. 是否先判断了代码范围并选择了合适模板？
2. 是否完整说明了当前代码的控制流、数据流和直接调用关系？
3. 是否把“详细”误写成了“全面”？
4. 是否删除了不影响理解的背景、边界和改进建议？
5. 是否每个概念只解释了一次，且没有重复结论？
